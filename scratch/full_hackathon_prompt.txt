# STEP 2 — TIME-AWARE RECOMMENDATION ENGINE

## Goal

Make Locora recommend experiences that can realistically fit into the user's available time.

This must be deterministic backend logic.

Do NOT rely on Gemini to decide whether something fits.

## Required calculation

For every candidate experience calculate:

```text
totalRequiredTime =
    travelToExperience
  + experienceDuration
  + returnTravel
  + safetyBuffer
```

Then compare:

```text
totalRequiredTime <= availableTime
```

If true:

```text
fitsTime = true
```

Otherwise:

```text
fitsTime = false
```

## Use existing location/recommendation data

Inspect the existing backend recommendation implementation before adding anything.

Reuse existing distance calculations and candidate information.

If actual travel-time information is available, use it.

If only distance is available, do not pretend it is exact travel time. Clearly distinguish estimated travel time from verified travel time.

## Required recommendation metadata

Every candidate should eventually expose information similar to:

```js
{
  travelTimeMinutes: 18,
  experienceDurationMinutes: 90,
  returnTravelMinutes: 18,
  bufferMinutes: 15,
  totalRequiredMinutes: 141,
  availableMinutes: 180,
  fitsTime: true,
  remainingMinutes: 39
}
```

Adapt the schema to the existing project.

## Hard filtering

Experiences that cannot fit the user's available window should not appear in the primary recommendations.

Do not simply give them a lower score.

The user specifically wants experiences that are realistically achievable.

## UI

Show a compact time breakdown on recommendation cards/details:

```text
18 min travel
90 min experience
18 min return
15 min buffer

Total: 141 min

Available: 180 min

✓ Fits with 39 min remaining
```

## Acceptance criteria

If the user has 3 hours and an experience requires 2h20m:

→ show it as fitting.

If an experience requires 3h20m:

→ exclude it from primary recommendations.

## Existing recommendation functionality must continue working.

# STEP 3 — LOCORA MATCH SCORE

## Goal

Create a transparent recommendation scoring system.

The score must NOT be generated by Gemini.

Gemini may later explain the score, but the actual score must be calculated by Locora's backend.

## Score dimensions

Use the Smart Context to calculate:

1. Interest match
2. Time fit
3. Budget fit
4. Distance
5. Availability
6. Rating/quality
7. Itinerary compatibility

Create a normalized score between:

```text
0–100
```

## Important

Design the scoring system so weights are centralized and easy to modify.

Example:

```js
const SCORE_WEIGHTS = {
  interest: 0.25,
  timeFit: 0.20,
  budget: 0.15,
  distance: 0.15,
  availability: 0.10,
  rating: 0.05,
  itineraryCompatibility: 0.10
};
```

These are starting values only. Inspect the existing recommendation logic and choose sensible weights that integrate with it.

Do not create a second scoring system if the project already has one. Upgrade the existing one.

## Hard constraints vs soft scoring

Hard constraints:

* Invalid destination
* Too far
* Cannot fit available time
* Clearly unavailable
* Cannot satisfy required accessibility
* Other existing Locora rejection rules

Soft scoring:

* Interest match
* Rating
* Distance preference
* Budget closeness
* Preference match

## Return score breakdown

Every recommendation should contain enough information for the UI to explain its score.

Example:

```js
{
  matchScore: 94,
  scoreBreakdown: {
    interest: 92,
    timeFit: 100,
    budget: 95,
    distance: 90,
    availability: 100,
    rating: 88,
    itineraryCompatibility: 100
  }
}
```

Adapt to the existing data model.

## UI

Display:

```text

```

Do not overdesign it.

The user should be able to understand why the recommendation ranked highly.

## Acceptance criteria

Same context + same candidate data should produce a stable score.

Gemini must not determine the numerical score.

## Existing candidate validation/rejection logic must remain intact.
